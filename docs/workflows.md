# 导入、会后整理与周计划

## 1. 先明确权威来源

在团队开始使用前，确认以下问题：

1. 任务状态以 TAPD、WBS、其他业务系统，还是 Vault 为最终权威？
2. 谁负责将主系统导出记录更新到工作台？更新频率是什么？
3. 谁能确认任务事实、容量、预测和基线？
4. 日期和工时口径是否统一？

v0.1.0 不连接远程主系统，不自动双向同步，不解决主系统与本地笔记的冲突。人工导入只是输入方式，不改变团队定义的权威来源。

## 2. 接入一个项目

### 建立映射

先创建项目、模块、人员记录并给它们稳定 ID。任务引用这些 ID；不要把同名成员当作同一个人，也不要把 Owner 自动当成每条任务的执行人。

建议从少量真实任务开始，逐条核对：

- 原系统 ID 是否稳定、是否有跨项目重号
- 项目、模块和执行人是否匹配
- 原定日期是否保持原值
- 当前预测是否附带前提
- 排入本周期的工时与剩余工时是否分别填写
- 状态究竟是开发完成、测试通过、发布还是验收
- 来源和更新时间是否足够判断信息新鲜度

### 导出与预览

运行“导入任务（CSV / JSON）”，粘贴导出的文本并查看预览。导出格式不匹配时，先转换到插件支持的字段，不能只改列名就忽略业务含义。

导入前做一次独立备份。预览中的校验和重复提醒应处理完毕；不要把“存在相同 ID”理解为可以覆盖当前笔记。取消导入应不产生任务写入，确认后再检查文件和工作台结果。

下面是字段含义示范，具体可用映射以导入预览为准：

```json
[
  {
    "id": "demo-import-001",
    "title": "【虚构】验证检索过滤规则",
    "project": "demo-project-001",
    "module": "demo-module-001",
    "executor": "demo-person-001",
    "status": "planned",
    "originalStart": "2026-09-28",
    "originalDue": "2026-10-02",
    "forecastDue": "2026-10-02",
    "remainingHours": 8,
    "allocations": [
      {"periodStart": "2026-09-28", "periodEnd": "2026-10-04", "hours": 6}
    ],
    "dependencies": [],
    "nextAction": "先准备边界测试数据",
    "source": "虚构 WBS 导出；仅作格式示范",
    "lastUpdated": "2026-10-01T08:00:00Z"
  }
]
```

这里的项目、模块和人员 ID 是虚构示例，请先建立对应记录或换成现有 ID。示例没有真实的 TAPD 工作区 ID、访问密钥或客户数据。

### 导入字段与重复规则

JSON 顶层支持任务数组，或者含 `tasks` 数组的对象。CSV 首行为字段名，使用英文规范键，不会自动猜测中文 TAPD 列名：

```text
id,title,project,module,executor,status,originalStart,originalDue,forecastDue,remainingHours,allocations,dependencies,nextAction,source,lastUpdated,risk,blocker,contact,coordinationDue
```

必需列为 `id`、`title`、`project`、`module`、`executor`、`status`、`originalStart`、`originalDue`、`forecastDue`、`remainingHours`、`nextAction`、`source`、`lastUpdated`。部分文本允许空值但会提醒缺失；空值不是已确认事实。

- `allocations` 在 CSV 中是 JSON 数组字符串；按照 CSV 规范给整个单元格加双引号，并把内部双引号写成两个双引号
- `dependencies` 可用 JSON 字符串数组，或用分号分隔任务 ID
- 标准状态使用 `planned` 等英文值；导入不猜测任意外部状态标签
- ID 以字母或数字开头，仅含字母、数字、点、下划线、冒号、连字符，最长 128 个字符
- 完全相同的重复任务跳过；同 ID 但字段不同视为冲突，整份预览不能应用，需使用明确审查的更新流程
- 非法日期、结束早于开始、负工时、未知状态、无效时间戳会报错；任何错误都禁止应用预览
- 未知导入字段和传入的 `path` 不写入；文件目标由工作台决定
- 引用缺失依赖会提醒；项目、模块、人员映射仍要人工核对

单条合法 CSV 示例（全部虚构，未排期）：

```csv
id,title,project,module,executor,status,originalStart,originalDue,forecastDue,remainingHours,allocations,dependencies,nextAction,source,lastUpdated
demo-import-002,【虚构】校验导出边界,demo-project-001,demo-module-001,demo-person-001,planned,2026-09-28,2026-10-02,2026-10-02,4,[],[],补充验收用例,虚构WBS导出,2026-10-01T08:00:00Z
```

非空安排的 CSV 单元格示例：`"[{""periodStart"":""2026-09-28"",""periodEnd"":""2026-10-04"",""hours"":4}]"`。复杂嵌套数据优先使用 JSON，避免手工转义错误。

### 导入之后

打开一条源文件和一个项目视图，检查同一条任务是否一致。回到人员视图确认周期负荷和容量不是由缺省零值制造的假象。外部导出可能已经过期，应保留其导出/更新时间，并再次核对关键状态。

## 3. 会后整理：规则只提建议

命令：“整理本次进展（离线规则辅助）”。

规则要求每行包含一个已知任务 ID 和明确的“字段: 值”。推荐输入：

```text
demo-task-002 状态: 开发完成; 剩余工时: 8
demo-task-002 下一步: 请成员乙补齐边界用例，再确认测试窗口
demo-task-002 风险: 只有测试资源按期到位，才可能本周期完成测试
```

以上为完全虚构的显式字段示例，只能提出相应字段变更。一般叙述如“开发已完成，测试还没开始”不会被当作整项任务完成。

支持的整理字段包括：`status/状态`、`forecastDue/预测日期`、`remainingHours/剩余工时`、`blocker/阻塞`、`risk/风险`、`nextAction/下一步`、`contact/联系人`、`coordinationDue/协调日期`。中文“开发完成”“测试通过”“已发布”“已验收”等明确状态可映射至相应标准值；模糊状态不会自动推断。一行有多个任务 ID 或没有已知 ID 时会保留为未匹配内容。预测/协调日期使用具体 `YYYY-MM-DD`，不使用“明天”。

离线规则可能只识别其中一部分，所以需要逐项确认：

1. 候选任务是否确实对应原文中的对象？同名、简称、含糊指代都要核对
2. 被改变的字段及旧/新值是否正确？
3. “未完成”“还没测试”“预计下周完成”等否定或预测是否保持原义？
4. 原文中的事实、预测和判断是否分开？
5. 来源、时间、下一步行动是否保留？

只应用经过明确检查的变更。其余内容保存为待整理笔记后再处理，不用猜测填空。原任务若已被其他编辑改变，应刷新并重新审查，不覆盖较新的信息。

本版规则能力有限，没有语义模型、外部检索、自动行动执行或“AI 已理解全部会议”的保证。

## 4. 每日负责人检查

可以按以下顺序快速检查：

1. 工作台的高优先级异常：阻塞、依赖、逾期、容量缺失或超载
2. 相关任务的来源及更新时间，确认不是过期信息
3. 协调对象、截止日期和下一步，明确需要谁做什么
4. 项目的原定日期与当前预测差异，说明影响
5. 人员跨项目容量，讨论取舍而非给人评分

“没有触发异常规则”只说明当前已读取数据没有触发已实现规则，不证明项目无风险。加载警告、没有容量、没有排期和缺失来源都值得单独确认。

## 5. 周计划与冻结

1. 选择真实讨论周期；不限于自然周
2. 检查个人工作日历、特殊日期与容量扣减
3. 填写每条任务明确排入本周期的工时
4. 先解决负荷超出容量和容量未知，再确认承诺
5. 查看冻结前任务列表，确认后创建基线
6. 后续只更新当前任务；新增范围在比较结果中单列

保留原基线才能讨论：哪些是原承诺，哪些是后来加入，哪些是范围变化，哪些日期发生了滑动。不要重写原快照来抹平偏差。

如需重新计划，应保留旧基线并创建新的明确命名版本，同时记录为什么改变承诺。不要把重新计划当成对过去承诺的追溯修改。

## 6. 生成并检查周会摘要

运行“生成周会摘要”，或从周计划入口预览摘要。检查：

- 周期和完成口径是否正确
- 已闭环是否被误读为已发布/验收
- 未闭环、取消和新增范围是否混淆
- 风险、阻塞、依赖和需要协调的事项是否仍有效
- 容量未知、负荷缺口和预测前提是否说明
- 来源路径和更新时间是否可用于复核
- 有无把建议写成决定、把预测写成事实

保存的 Markdown 是一次汇总快照。之后源记录变化，不会让以前发出的报告自动更新；生成新版时请标明时间。插件不会自动把报告发给他人。

## 7. 恢复与排错

### 工作台是空的

确认当前设置的数据目录、文件是否在该目录内、frontmatter 是否有合法 `workbench` 和字符串 `id`。普通 Markdown 任务清单不会自动被识别为结构化任务。

### 有任务没有显示

先展开数据校验提醒；检查重复 ID、损坏 YAML、字段类型，以及当前项目/搜索筛选。不要立即重新导入同一份任务造成更多重复。

### 人员显示未知

检查人员记录是否存在已确认的 `capacity.hoursPerDay` 或 `capacity.weeklyHours`。未知是诚实的资料状态，只有获得真实容量信息后才应补充。

### 负荷看起来太小

检查所选周期和 `allocations`。任务可能有剩余工时却尚未排期，或者已被排在其他周期。不要把未知安排当作没有需求。

### 需要撤回一次更新

先核对原记录与备份/Obsidian 文件恢复能力。工作台不是版本控制系统；建议定期备份。不要删除基线或来源记录来伪造旧状态。

## 8. 会议收件、预览与行动

工作台的一级导航为“工作台 / 项目 / 人员 / 会议 / 资料 / 周计划”。项目详情分为“概览 / 任务 / 人员 / 会议 / 文档 / 原型”；从项目进入的内容仍是同一份 Vault 记录。会议入口同时保留阻塞协调与既有决策记录。

1. 登记会议名称、时间、项目、参与人，可补充模块与迭代
2. 粘贴或导入已有的纪要文本；保留原文、来源和录音/转写 URL
3. 在预览中分开检查讨论、建议、已确认决定及未决项
4. 核对行动关联的已有任务、负责人和明确截止日期
5. 为本次会议固定资料的确切版本，再确认保存

录音和转写 URL 只是来源链接。插件不录音、不下载音频、不提供转写，不把“建议采用新版”自动升级为“已确认采用”。规则生成的候选项必须经人工检查；不匹配或不确定内容保留原文，不能当作 AI 已判定的事实。

保存会议不会自动改变任务状态、工时或承诺日期。若要更新任务，单独使用字段预览与确认流程；若要采用资料版本，单独确认采用。会议中的行动状态与任务状态是两份含义不同的记录，不会静默联动。

## 9. 资料收件与明确采用

### 文档或原型的新版本

在“资料”或项目的“文档 / 原型”中登记资料，核对名称、资料 ID、版本号、项目、提供者与来源。同一资料收到修订时，保留原 `materialId`，创建新的版本 ID 和版本号；不要覆盖旧文件来伪装成同一版本。

版本详情保留原始链接/文件、版本历史、摘要、人工变更说明、评审问题、预览结果及任务/会议引用。版本列表以名称、类型、版本、状态、更新时间和打开入口呈现。这里没有自动内容差异引擎；变更说明来自人类记录，不表示插件比较了原型视觉或文档全文。

### 采用与固定引用

1. 打开目标版本与来源，核对实际内容
2. 检查评审问题和网络/登录/运行要求；未知应保持未知
3. 明确确认采用该版本，写入新的 Adoption 记录
4. 查看哪些任务和会议仍固定在旧版本；只在需要时单独确认调整引用

最新收到、已评审、已采用分别表达不同含义。收到 v0.3 时，采用记录仍可指向 v0.2；之后采用 v0.3，也不会让按 v0.2 开始的任务或会议自动切换。旧版本及旧采用记录继续保留，便于追溯当时的依据。

## 10. 原型包收件与外部应用查看

支持单 HTML、包含相对资源的文件夹、ZIP、HTTP(S) 在线 URL。文件夹导入保留选中的根目录和相对资源层级，不把文件名拍平。ZIP 保留原包和展开文件；输入先完整检查，确认前不写入正式版本。线上 URL 只登记链接，不抓取或复制站点。

### 入口与预览

- 本地原型入口必须是包内明确选择的 `.html` 或 `.htm`；多个候选入口需确认实际使用哪一个
- 文档附件不要求 HTML 入口；不能把普通文档误报为可运行原型
- 先核对清单、入口和来源，再确认导入；取消不能创建一个被误认为已采用的版本
- 未实际走查前，预览结果保持未知；通过或失败需填写检查记录
- 网络、登录及服务器要求由人核实并记录，不以文件扩展名或压缩包校验推断

### ZIP 边界

当前接收 ZIP32 的 stored/DEFLATE 压缩、ASCII 或 UTF-8 名称。限制为原包 20 MiB、展开总量 50 MiB、单文件 10 MiB、最多 500 条文件/目录记录、路径 1024 UTF-8 字节、深度 32；解压比例最高 200 倍，并为小文件保留 1 KiB 余量。

拒绝路径穿越、绝对路径、Windows 路径、编码分隔符、保留名称、大小写/Unicode 别名冲突、文件/目录冲突、重复条目、符号链接和特殊文件；也拒绝加密、多卷、ZIP64、不完整头/描述符与 CRC 不一致的归档。失败时应换取来源方提供的有效普通包，不通过关闭保护强行导入。

这些检查保护导入边界和文件完整性，不扫描全部恶意代码，不证明原型安全，也不会将预览自动标为通过。

### 打开边界

“打开”把已确认的入口交给系统默认外部应用（由文件关联决定，可能是浏览器或编辑器），不在 Obsidian 中嵌入 iframe、执行脚本、托管页面或启动本地服务器。本地入口仅支持桌面 Electron 适配器；移动端和不具备该适配器的宿主会明确提示不支持。线上 HTTP(S) URL 可通过桌面或移动端的外部浏览器打开。

原型在浏览器中仍可能运行脚本、请求外网、要求登录或无法在 `file:` 环境运行。按来源可信度决定是否打开；如需 Web 服务器、构建步骤或特定运行环境，应记录要求并由使用者另行安排，插件不静默代办。
